# Final Reflection
Throughout this course, I gained a much deeper understanding of how real-time embedded systems are designed and implemented. Before taking this class, my primary focus when writing software was simply producing the correct output. This course changed the way I approach embedded programming by emphasizing timing, scheduling, synchronization, and overall system architecture. I learned that in real-time systems, producing the correct answer is only part of the problem—the answer must also be produced within a predictable and guaranteed amount of time.

For my capstone project, I developed a dual-core FreeRTOS avionics monitoring and fault-tolerant telemetry system that demonstrated queues, event groups, direct task notifications, heartbeat monitoring, and worst-case execution time analysis. Integrating these concepts into one complete system was significantly more challenging than implementing each feature individually. Designing communication between multiple tasks while maintaining the proper behavior required careful planning and extensive debugging. Measuring worst-case execution time also proved more difficult than expected because debugging output and task scheduling influenced the measured execution times. Working through these challenges helped me better appreciate how timing analysis is performed in real embedded software projects.

If I were to complete this project again, I would spend more time designing the software architecture before beginning implementation. Early in the semester, I focused primarily on getting individual tasks to function correctly. Looking back, investing more effort in planning task priorities, communication paths, and synchronization mechanisms would have simplified the integration process later in the project. I would also incorporate performance measurement and debugging tools from the beginning instead of adding them near the end. Finally, I would document my design decisions throughout development so that producing the final portfolio and technical documentation would require much less effort.

The most valuable lesson I learned from this course is that successful embedded software development requires balancing functionality with predictability. FreeRTOS provides many synchronization mechanisms, but selecting the appropriate one depends on latency requirements, communication patterns, and system architecture. Understanding how queues, event groups, semaphores, mutexes, and direct task notifications work together has given me practical experience that extends far beyond simply learning their APIs. I also developed a much greater appreciation for worst-case execution time analysis and schedulability testing, which are essential concepts in safety-critical applications.

This course has strengthened my interest in embedded systems engineering, particularly within the aerospace, defense, and automotive industries. The concepts covered throughout the semester closely resemble the software architecture used in flight computers, automotive electronic control units, robotics, and industrial automation systems. Completing this capstone project provided experience integrating multiple real-time concepts into one system while documenting the design in a professional engineering portfolio.

Overall, this course fundamentally changed the way I think about embedded software. Instead of only considering what the software should do, I now think about when it should execute, how tasks should communicate, how failures should be handled gracefully, and how system performance can be verified through timing analysis. These skills will be valuable throughout my engineering career as an engineer in the automotive/defense industry, and I feel much more prepared to discuss and defend a complete embedded systems project during future technical interviews.
